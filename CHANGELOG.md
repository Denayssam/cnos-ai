## [v8.27.0] - The Subconscious Patch

**Objetivo:** Phase 3.3 cierra dos huecos de housekeeping que el motor venía dejando para que el humano (o el @manager gastando iteraciones) los limpie a mano: (1) **Worktrees huérfanos acumulándose en `.fluxo/worktrees/`** después de sesiones killed, exit_worktree(discard) que falló silencioso, o coordinación rota entre dos ventanas de VS Code sobre el mismo repo — el inventario crecía sin freno hasta que `git worktree list` se volvía ruido. (2) **Memoria de proyecto inexistente** — cada sesión nueva re-descubría desde cero las mismas reglas técnicas (este proyecto usa pnpm, este webhook necesita ese header, este vite.config requiere base prod específico) que ya habían quedado claras en sesiones previas. v8.25.0 puso el botón Restore (control humano sobre el output del agente); v8.27.0 pone las dos disciplinas de "subconsciente" que faltaban: el motor limpia su propia basura al arrancar, y guarda durable lessons al terminar — sin gastar iteraciones del @manager, sin pedirle al humano que recuerde los rituales.

- **Auto-Cleanup de Worktrees Huérfanos (`src/utils/cleanupRegistry.ts` — NEW):** Nueva función pura `cleanupOrphanedWorktrees(workspacePath): string[]`. Lectura defensiva de `.fluxo/active_worktree.json` (si está corrupto o ausente, treat as "no active worktree" y limpia TODO; clean session start lo regenera). Escaneo de `.fluxo/worktrees/` con `fs.readdirSync({withFileTypes: true})`, filtro a directorios cuyo `entry.name !== activeBranchName`. Por cada huérfano ejecuta el ritual completo de Git en orden: (1) `git worktree remove --force <path>` con timeout 15s — el `--force` es obligatorio porque los huérfanos típicamente cargan residue uncommitted de sesiones killed; sin él git refuse con "contains modified or untracked files"; (2) `git worktree prune` con timeout 10s — sweepea entries stale en `.git/worktrees/<name>` que el remove pudo haber dejado o que un remove previo creó; (3) `git branch -D <branch>` con timeout 10s — bypass del check "not fully merged" que bloquearía la deletion porque la branch contiene el anchor commit unmerged; el "branch not found" se silencia porque algunas versiones de git ya borran la branch en el step 1; (4) `fs.rmSync(<path>, { recursive: true, force: true, maxRetries: 3 })` — fallback defensivo para Windows donde a veces git suelta su bookkeeping pero un file handle sigue colgando del árbol. Cada step tiene try/catch independiente — un orphan stuck no aborta los demás. Sanity gate al inicio: `git rev-parse --is-inside-work-tree` con stdio:'pipe' — si el workspace no es git repo (típicamente porque alguien copió `.fluxo/` de otro proyecto), retorna `[]` sin spam de stderr. Retorna la lista de branch names destruidos para telemetry; el caller logea `[Fluxo Cleanup] Destroyed N orphan worktree(s): <list>` solo si N > 0.
- **Wiring del cleanup en activación (`src/extension.ts`):** La función `cleanupLogsOnActivation()` (que ya pruneaba `.fluxo/backups/` a los 30 archivos más recientes desde versiones previas) ahora invoca `cleanupOrphanedWorktrees(wsPath)` envuelto en su propio try/catch defensivo. Razón del wrapper: aunque la función del servicio ya tiene defensas internas por step, una excepción top-level inesperada no debe poder bloquear la activación de la extensión bajo ninguna circunstancia — la cleanup pass entera es best-effort. Logging silencioso por console (no UI noise — el usuario nunca ve el cleanup pasar a menos que abra la consola del extension host).
- **Background Memory Extraction (`src/services/extractMemories/extractMemories.ts` — NEW + `src/agentEngine.ts` exports):** Nuevo servicio asíncrono inspirado en el "subconscious" pattern de Claude Code (memory tool) y Cursor (persistent project notes): después de una completion exitosa, una pasada en background destila la conversación a UN bullet durable y lo appendea a `.fluxo/memory.md`. Constraints arquitectónicos críticos documentados en el header del archivo: (1) **Fire-and-forget** — el agent loop nunca awaitea; siempre llamado vía `.catch()` en el call site para que un network blip / API timeout / quota exhausted nunca rompa el success exit. (2) **Cheap model** — default `gemini-2.5-flash-lite` (el más rápido del catálogo default), fallback a `config.workerModel` si el lite no está accesible; spending un premium model en single-bullet summarization sería desperdicio. (3) **Short budget** — `maxTokens: 1024`, contrato estricto con el LLM "single Markdown bullet OR literal NONE". (4) **NONE-filter** — chequeo literal `raw.toUpperCase() === 'NONE'`; sin esto, cada task escribiría un vacuous "the agent edited a file" que polutearía memory.md hasta volverse inservible. (5) **Project-scoped** — `.fluxo/memory.md` versionable junto al resto del proyecto; un team member que clona el repo hereda el conocimiento acumulado. Append + create-if-missing; nunca rewrite ni condense (preserva el log completo). Trim del history a las últimas 30 messages, cap por-message de 2KB, drop de mensajes `[CONDENSER]`/`[COMPACTED MEMORY]` (ruido sin signal de proyecto), y flatten de roles (rinde cada message como `[role] content` en un user payload único — sidesteppea las constraints de schema assistant↔tool del API). Defensive: si el LLM ignora el contrato y emite prosa, se intenta extraer la primera línea bullet (`- ` o `* `); si no hay ninguna, treat as NONE. Top-level try/catch swallow + console.error para que `unhandledRejection` nunca leakee al runtime.
- **Export de `callOpenRouterBlocking` y `ApiResponse` desde el agentEngine:** El servicio extractMemories necesita issuir su propia llamada LLM corta sin re-implementar endpoint resolution / API key picking / OpenRouter headers / Gemini-direct dispatch. La solución más limpia: promote `callOpenRouterBlocking` y la interface `ApiResponse` a public surface del engine (vía `export`), consumirlos desde el servicio. Comentarios al lado de ambos exports documentan que son la transport canónica del engine y los services los consumen como RPC primitive — futuros services (next: `src/services/summarizeOnExit/`, `src/services/scoutForRegressions/`) usan el mismo patrón.
- **Wiring fire-and-forget en `agentEngine.ts`:** Llamada a `extractMemories(messages, config, workspacePath).catch(() => {})` insertada justo ANTES de los dos `yield { type: 'streamEnd' }` de los success paths reales: (a) la rama del completion-signal (Orchestrator's Report / ALL STEPS COMPLETE), después de que el Quality Gate pase verde o se skipee (no QG required); (b) la rama del text-only no-tools después de ghostRetries exhaustos, también después del QG pass. Los demás `streamEnd` (BUILD_FAILED, plan brake, abort, MAX_ITERATIONS, circuit breaker) NO disparan el extractor — esos son fail exits y guardar memoria de un fail rara vez aporta signal útil; pollution de memory.md sería peor que el silencio.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.27.0`.
- **Resultado:** Cierra Phase 3.3. Dos disciplinas de "subconsciente" que el motor ahora ejecuta sin gasto cognitivo del @manager ni intervención humana. (1) **Cleanup automático**: cada arranque de VS Code, el inventario de worktrees queda en su mínimo legítimo (solo el activo); años de sesiones killed o exit failures no acumulan disco ni clutter; el ritual de cleanup ya no depende de que alguien recuerde correr `git worktree prune`. (2) **Memoria automática**: cada task exitoso tiene la posibilidad de aportar UN bullet durable a `.fluxo/memory.md` (filtro NONE garantiza que solo aporte si genuinamente se descubrió algo nuevo); sesiones futuras que incluyen memory.md en context arrancan con todo el conocimiento que sus predecesores rediscovered. La latencia de extracción no se ve — fire-and-forget en background después del streamEnd. Phase 4 (mutex + DAG conflict resolution), Phase 3 (RBAC + MCP registry + Discovery), v8.21.0/v8.22.0/v8.23.0/v8.23.1/v8.24.0/v8.25.0/v8.26.0/v8.26.1 — todo intacto. Pre-condición arquitectónica para Phase 4 + memoria persistente lista.

## [v8.26.1] - The Sherlock Schema-Closure Hotfix

**Objetivo:** Hotfix crítico para una violación del contrato API descubierta en el bloque de rechazo del Sherlock Auditor (`src/agentEngine.ts`). Cuando Sherlock decidía bloquear un batch de tool calls (porque detectaba comportamiento rogue, redundant declaration, syntax target sospechoso, etc.), el motor empujaba un mensaje `role: 'user'` con el directive de recuperación y ejecutaba `continue` para reiniciar el outer loop — pero NUNCA emitía los mensajes `role: 'tool'` correspondientes a los `tool_call_id` del array `tcToExecute` que acababa de bloquear. El siguiente `callOpenRouterBlocking` request crashaba con `HTTP 400: An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`. La sesión moría en seco la primera vez que Sherlock disparaba en una conversación con tool calls — un modo de fallo equivalente al que v8.23.1 cerró para los condensers, pero en una capa distinta del motor.

- **Schema Closure en el Sherlock-rejection path (`src/agentEngine.ts`):** Justo ANTES del `messages.push({ role: 'user', content: 'CRITICAL AUDIT FAILURE...' })` que inyecta el directive de recuperación, se añade un `for (const tc of tcToExecute)` que empuja un mensaje `{ role: 'tool', tool_call_id: tc.id, name: tc.function.name, content: '[AUDIT BLOCKED] The Sherlock Auditor rejected this tool call. See the critical audit failure message below.' }` por cada call bloqueada. Esto satisface matemáticamente el invariante 1-to-1 del schema OpenAI/OpenRouter: todo `tool_call` en el assistant message previo recibe su `tool` answer correspondiente, en orden, antes del próximo turn. El `continue` posterior queda intacto. El ordering del turn pasa a ser exactamente: `assistant(tool_calls)` → `tool × N` (stubs bloqueados) → `user` (recovery directive) → `next assistant` — la cadena que la API exige.
- **Disciplina compartida con v8.23.1:** Mismo principio que la Safe Compaction Patch — nunca rompas el pairing assistant→tool. La diferencia es que v8.23.1 lo aplicó a las dos rutinas de condenser (que antes spliceaban y dejaban orphans), y v8.26.1 lo aplica al Sherlock-rejection path (que omitía completamente las respuestas). Las dos correcciones cierran la misma clase de bug en lugares estructuralmente distintos del motor; documentar el invariante explícitamente en ambos sitios reduce la probabilidad de un tercer regress en futuro.
- **Stub message intencionalmente corto:** El payload `[AUDIT BLOCKED]` es un one-liner — sin stack trace, sin context. Razón: el directive completo de recuperación ya se push-ea como user message dos pasos después; duplicarlo en cada tool stub solo infla tokens. El stub solo necesita cumplir el contrato del schema y dirigir la atención del LLM al user message que viene a continuación ("See the critical audit failure message below").
- **Sin cambios al Sherlock auditor mismo:** La heurística de detección (`revisorResult.content.toUpperCase().includes('ERROR:')`), el modelo auditor (`anthropic/claude-3-haiku` para anthropic, `openai/gpt-4o-mini` para openai, default existente para los demás), el `syntaxTargets` recovery directive — todo intacto. Esta versión arregla únicamente la closure del schema; el comportamiento auditor cuando Sherlock rechaza queda exactamente igual de estricto.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.26.1`.
- **Resultado:** Cierra el segundo modo de fallo "API 400 por orphan tool_call" descubierto post-v8.22.0. Sesiones con auditor agresivo (típicamente cuando el agente toca código sensible que dispara las heurísticas de redundant declaration / rogue behavior) ya no mueren a la primera rechazo de Sherlock. La cadena de recovery completa ahora ejecuta end-to-end: agente emite tool_calls → Sherlock audita → rechaza → motor cierra el schema con stubs bloqueados + inyecta recovery directive → siguiente iteración → LLM ve el contexto completo y reformula su approach. Phase 4 (mutex + DAG conflict resolution), Phase 3 (RBAC + MCP registry + Discovery), v8.21.0/v8.22.0/v8.23.0/v8.23.1/v8.24.0/v8.25.0/v8.26.0 — toda la stack acumulada intacta. Single-file hotfix, ningún cambio de comportamiento más allá del schema closure.

## [v8.26.0] - The MCP Discovery Patch

**Objetivo:** Cerrar Phase 3.4 — la pre-condición arquitectónica para que Fluxo pueda interactuar autónomamente con flujos de n8n y SaaS externos via MCP en Phase 4. Hasta v8.25.0 toda la integración MCP vivía en un único archivo monolítico de 281 líneas (`src/mcpClient.ts`) que mezclaba: gestión del transport stdio, descubrimiento de tools, RBAC inference, resolución de placeholders, y el dispatch de calls. Esa monolitización funcionó para v8.18.x → v8.20.x donde MCP solo exponía `tools` (funciones callables), pero no escala a Phase 4: los servidores n8n + Notion + Linear + Supabase exponen también `resources` (URIs leíbles — workflows JSON, schemas de DB, plantillas de prompt, configuraciones), y los agentes necesitan poder enumerarlos antes de llamar tools que operen sobre ellos. Sin discovery, el LLM hallucinaba URIs ("¿existe `/workflows/onboarding.json` en este servidor n8n?" → no → tool falla → ciclo de retry) idéntico al modo de fallo que v8.22.0 cerró para paths locales pero no para recursos remotos. v8.26.0 trae las dos disciplinas que faltaban: **extracción de la lógica MCP a una capa de servicios dedicada** (`src/services/mcp/`) sin regresiones, y **una herramienta de descubrimiento atómica** (`list_mcp_resources`) inyectada en los toolsets del @planner y @manager.

- **Refactor a Service Layer (`src/services/mcp/client.ts` — NEW; `src/mcpClient.ts` — DELETED):** Toda la lógica del antiguo `mcpClient.ts` se movió bit-a-bit al nuevo path bajo el namespace `services/mcp/`, preservando explícitamente todos los invariantes que el motor depende de: (1) **Promise.allSettled parallel boot** — los servers se conectan en paralelo, un fallo no aborta la batch, el timeout per-server sigue en 30s, las transports que pierden el race se cierran explícitamente para no leakear procesos node huérfanos; (2) **RBAC category map** — `inferCategories` sigue keyed por `mcp_<server>_<tool>` y mergea categories explícitas (config-pinned) con inferidas (heurística regex), consumido sin cambios por `applyMcpRbac` en `agentEngine.ts`; (3) **Placeholder resolution** — `_resolveServerConfig` aplica `resolvePlaceholders` (de `mcpRegistry`) a `command`, cada string en `args`, y cada valor en `env` antes de instanciar el `StdioClientTransport`; (4) **`ensureStarterPack` idempotente** — re-runs sobre un workspace con `.fluxo/mcp_servers.json` existente son no-op silencioso. La clase `McpSwarmClient` mantiene exactamente la misma superficie pública (`initialize`, `getMcpTools`, `getMcpToolCategories`, `callMcpTool`, `destroy`). Header del nuevo archivo documenta los cuatro invariantes como contrato auditable para futuros refactors. Decisión de diseño explícita: `mcpRegistry.ts` y `mcpConfigWriter.ts` SE QUEDAN en `src/utils/` porque son utilidades stateless de I/O (catálogo built-in + writer atómico de JSON) consumidas tanto por el client como por la CLI standalone (`src/commands/mcp.ts`); promocionarlas a `services/` mezclaría dos niveles de abstracción y rompería los imports de la CLI sin beneficio arquitectónico.
- **Imports actualizados sin breakage:** Solo `src/extension.ts` referenciaba el viejo path; cambia `import { McpSwarmClient } from './mcpClient'` → `'./services/mcp/client'`. `src/commands/mcp.ts` no se toca — solo importaba de `mcpRegistry` y `mcpConfigWriter`, ambos sin moverse. Comentarios de docstring en `agentEngine.ts:83` y `:313` actualizados de `mcpClient.inferCategories` → `services/mcp/client.inferCategories` para que la doc del RBAC siga siendo navegable desde un grep. Cleanup post-build: el `out/mcpClient.js` huérfano (tsc no auto-purga compilados de fuentes eliminadas) se borra manualmente para que el `.vsix` no shippee un archivo muerto.
- **`McpSwarmClient.listResources(serverName)` — NEW método público (`src/services/mcp/client.ts:319-363`):** Validación de input (`server_name` no vacío y string), validación de servidor conectado (si el alias está mal, sugiere alternativas listando los servers actualmente conectados via el nuevo helper `getConnectedServerNames()`), `Promise.race` contra timeout de 5s, formateo human-readable (`uri | name | mimeType | description` por línea, descripción truncada a 200 chars, lista capada a 50 entries con nota `…(showing first 50 of N)`). Defensive: si el server no advertise `resources/list` capability el SDK throwa — se traga y retorna falla clean en vez de exception cruda al motor.
- **`ListMcpResourcesTool` — NEW (`src/tools/ListMcpResourcesTool/index.ts`):** Tool atómico de descubrimiento. `TOOL_DEF.name = 'list_mcp_resources'`, parámetro requerido `server_name` (string, alias as it appears in `.fluxo/mcp_servers.json`, case-sensitive). Descripción orienta al LLM a usarlo ANTES de llamar un `mcp_<server>_<tool>` que opere sobre un recurso remoto, para evitar hallucination de URIs (mismo patrón que `get_code_structure` precediendo un refactor). El `execute()` síncrono es un placeholder defense-in-depth que retorna `[SYSTEM ENGINE ERROR]: list_mcp_resources must be intercepted by the McpSwarmClient callback in extension.ts` si el callback no está disponible (e.g. corriendo fuera del extension host); en producción nunca se alcanza porque el intercept del engine fires primero.
- **Engine intercept + callback wiring (`src/agentEngine.ts` + `src/extension.ts`):** Nueva firma de `runAgentLoop` con parámetro opcional `listMcpResourcesCallback?: (serverName: string) => Promise<{success, output}>` siguiendo exactamente el patrón de `callMcpToolCallback` / `getCodeStructureCallback` / `replaceSymbolCallback`. Intercept en el dispatch del engine (junto al de `mcp_*`) que valida `server_name`, emite `🔌 MCP: Discovering resources on <name>…` como thinking event, y awaitea el callback. Propagado a las tres llamadas internas a `runAgentLoop`: el DAG dispatcher, el planner spawn (que anteriormente recibía `undefined` para `getDiagnosticsCallback` por ser read-only — ahora recibe el callback de discovery porque el planner SÍ lo usa), y el swarm spawn (cada sub-agente re-aplica su propio RBAC sobre el universo de tools, así que si la categoría les corresponde, también pueden discovery). En `extension.ts`, el callback inline `async (serverName) => await _mcpClient.listResources(serverName)` se pasa como último argumento al `runAgentLoop` principal — el `McpSwarmClient` es el dueño de las stdio transports vivas, así que el routing back-to-extension-host es obligatorio.
- **Wiring a planner + manager toolsets (`src/agents.ts`):** `'list_mcp_resources'` añadido al final del array `tools` del @planner ([:509](src/agents.ts#L509)) y del @manager ([:616](src/agents.ts#L616)). Razón de la elección de roles: el @planner usa discovery durante la phase de research previa al `IMPLEMENTATION_PLAN.md` (necesita saber qué workflows n8n existen antes de planear cómo integrar uno); el @manager lo usa durante orchestration (decidir si dispatch un sub-agente con un mandato que toque un recurso remoto, o si hay que crear el recurso primero). Los demás roles (@coder, @designer, @dashboard, @payments) NO reciben el tool — por Principle of Least Privilege, quien implementa no necesita enumerar el catálogo, solo necesita los `mcp_<server>_<tool>` específicos que el RBAC ya le filtra.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.26.0`.
- **Resultado:** Cierra Phase 3.4. La superficie MCP queda particionada en tres capas auditables: **service** (`src/services/mcp/client.ts` — gestión de transports + lifecycle + cache), **utils** (`src/utils/mcpRegistry.ts` + `src/utils/mcpConfigWriter.ts` — catálogo built-in + I/O atómico), y **tool surface** (`src/tools/ListMcpResourcesTool/index.ts` + el ya existente patrón `mcp_<server>_<tool>` — la API que ven los agentes). El @planner y @manager ahora tienen un primitive de discovery atómico equivalente al `get_code_structure` que ya tienen para código local: enumerar antes de actuar, evitar hallucinations de URI, y permitir que la planificación opere sobre el catálogo real de recursos remotos. Phase 4 (mutex + DAG conflict resolution), Phase 3 RBAC, v8.21.0 cognitive strictness, v8.22.0 path sanitizer, v8.23.0 LSP passive feedback, v8.23.1 safe compaction, v8.24.0 Financial Killswitch, v8.25.0 North Star UI + Aider Write-Block — todo intacto. Esta versión es puramente arquitectónica + capability extension; ningún cambio de comportamiento del motor ni de cognitive subsystems. Pre-condición arquitectónica para Phase 4 (n8n + SaaS automation flows) lista.

## [v8.25.0] - The North Star Patch

**Objetivo:** Cerrar dos brechas que sobrevivían a toda la maquinaria defensiva acumulada de v8.18.x → v8.24.0. (1) **Falta de un control humano de "undo"**: el motor crea checkpoints atómicos via `createSilentCheckpoint` desde v8.15.0 — y el helper `rollbackToLastCheckpoint` ya existía en `gitSafety.ts` desde el día uno — pero NUNCA estaba expuesto al usuario. Si el agente metía una refactorización ruidosa y el Quality Gate no atrapaba el desastre semántico (typecheck pasa, semántica está rota), el humano tenía que abrir terminal y correr `git reset --hard HEAD~1` a mano sabiendo que existía un anchor. La mayoría de usuarios ni siquiera sabía que el anchor existía. (2) **`write_file` sigue siendo un arma de destrucción masiva**: incluso con todas las heurísticas de prompt que orientan al agente hacia `replace_block` / `replace_symbol` / `replace_lines` / `search_and_replace` / `insert_lines`, bajo presión el LLM seguía emitiendo `write_file` sobre archivos existentes — re-emitiendo un `App.tsx` completo "con un pequeño fix adentro" y borrando 200 líneas de código no relacionado en el proceso. Las defensas eran prompt-level (una sugerencia que el LLM podía ignorar), no físicas. v8.25.0 trae las dos disciplinas que faltaban, ambas inspiradas en la arquitectura de agentes CLI maduros: **Compare and Restore al estilo Cline** (un control físico en la UI para revertir el último checkpoint con un click) y **Write-Block estricto al estilo Aider** (prohibición física de sobrescritura, forzando el editing tool de tipo diff/AST como único camino para tocar código existente).

- **Restore Workspace Only — UI (`src/extension.ts` + `media/main.js` + `media/style.css`):** Nuevo botón `<button id="restore-btn" class="header-btn restore-btn">⟲</button>` añadido al `header-right` del panel principal, posicionado entre el `sentinel-btn` y el `streaming-info-btn`. El glyph `⟲` (anti-clockwise gapped circle arrow) se eligió específicamente para distinguirlo del `↶` de "deshacer último carácter": esto deshace una unidad semántica completa (el último turn del agente), no un microedit. Tinted en ámbar (`rgba(245, 158, 11, *)`) en `style.css` para telegrafiar "destructive but safe" — ámbar y no rojo porque el rojo está reservado al estado activo del Sentinel. El listener en `main.js` (`restoreBtn?.addEventListener('click', ...)`) emite `vscode.postMessage({ type: 'restoreWorkspace' })` sin más lógica del lado del webview; toda la confirmación y la ejecución viven extension-side por seguridad.
- **Restore Workspace Only — handler (`src/extension.ts`):** Nuevo `case 'restoreWorkspace':` en `_handleMessage`. Flujo: (a) verifica que `vscode.workspace.workspaceFolders` exista (sin workspace activo retorna warning), (b) abre un `vscode.window.showWarningMessage` MODAL con `{ modal: true }` y un único botón "Restaurar" — el modal explica explícitamente que `git reset --hard HEAD~1` es destructivo, que el WIP humano se preserva por la garantía de Smart Auto-Commit (v8.16.7), y que la acción no se puede deshacer desde la UI; (c) si el usuario cancela, broadcast a la panel `{ type: 'restoreResult', success: false, output: 'Restauración cancelada por el usuario.' }`; (d) si confirma, llama atómicamente `rollbackToLastCheckpoint(wsPath)` (el helper existente en `gitSafety.ts:128`), broadcast el resultado al panel, y muestra `showInformationMessage` o `showErrorMessage` según el outcome. Import nuevo: `import { rollbackToLastCheckpoint } from './utils/gitSafety';` añadido al header de `extension.ts`. Inspirado directamente en la UX de Cline ("Compare and Restore" pero sin la parte del compare per-message — un solo botón global, una sola acción), porque el caso de uso del 95% es "el último turn rompió todo, vuélveme al estado anterior".
- **Strict Aider Write-Block (`src/tools/FileWriteTool/index.ts`):** Hard-block físico al inicio de `execute()`, después de `safePath()` (para tener el path absoluto resuelto) y antes de `checkSyntax` + `acquireLock` (no malgastar trabajo si vamos a rechazar). Si `fs.existsSync(fp)` retorna `true`, el tool retorna inmediatamente: `{ success: false, output: '[SYSTEM BLOCK] Prohibido usar write_file en archivos existentes. Debes usar replace_block o replace_symbol.' }`. NO hay flag healing_mode que lo bypase — la prohibición es absoluta para forzar al LLM hacia tools de tipo diff/AST que la base de código ya tiene (`replace_symbol` que opera por LSP, `replace_lines` con coordenadas explícitas, `search_and_replace` con verbatim matching, `insert_lines` para inyecciones masivas, `replace_block` con search_snippet/replace_snippet). El comportamiento está alineado con la disciplina unified-diff de Aider: si vas a tocar código existente, demuéstralo con coordenadas o un fragmento verbatim, no re-emitas el archivo entero.
- **Whitelist `.fluxo/` (`src/tools/FileWriteTool/index.ts`):** Excepción explícita y documentada al Write-Block: paths que comienzan con `.fluxo/` o `.fluxo\` (cubre POSIX y Windows separators) están exceptuados del bloqueo. ## [v8.24.0] - The Financial Killswitch Patch

**Objetivo:** Cortar de raíz un modo de fallo nuevo y caro descubierto en producción: cuando el entorno Windows pierde la referencia al shell del sistema (Node devuelve `spawnSync ENOENT cmd.exe`, típicamente porque `%ComSpec%` quedó vacío tras un reload de VS Code o `System32` se cayó del PATH del extension host), el `RunCommandTool` correctamente desde v8.16.8 retornaba un payload `[YIELD TO HUMAN — Node Environment Error]` con instrucciones explícitas: NO retry, NO PowerShell evasion, NO node -e hacking — restaurar el entorno y volver a empezar. Pero el motor seguía empujando ese payload a `messages` como un tool result normal y devolviéndoselo al LLM, que ignoraba el "DO NOT retry" y entraba en un panic loop hallucinando MCP servers, comandos PowerShell alternativos, y wrappers `node -e` para "esquivar" un problema que vive afuera del proceso. Una sesión real quemó las 25 iteraciones completas (~$1.50 en API credits) intentando "arreglar" un cmd.exe ausente — algo que NINGUNA cantidad de prompting o tooling puede arreglar desde adentro de Node. v8.24.0 cierra esta sangría con un killswitch estructural: el payload nunca llega al LLM, el loop muere antes de la siguiente llamada API, y el control vuelve al humano con un mensaje claro.

- **Hard Engine Abort on Fatal OS Errors (`src/agentEngine.ts`):** Nuevo bloque `[Financial Killswitch — v8.24.0]` insertado JUSTO ANTES del primer `yield { type: 'toolResult', ... }` de cada iteración del tool loop (línea ~1677, después del `try/catch` que captura el `result` y antes de que cualquier mensaje se pushee a `messages` o se reporte a la UI). Si `typeof result.output === 'string' && result.output.includes('[YIELD TO HUMAN')`, el motor ejecuta exactamente esta secuencia: (1) yield `toolResult` con el payload original — el usuario VE qué tool produjo el yield y cuál fue el mensaje exacto; (2) debugLog `[Financial Killswitch] '<tool>' returned YIELD_TO_HUMAN — aborting loop to prevent API drain`; (3) yield `streamChunk` con un mensaje final claro que combina el sentinel `🛑 [FINANCIAL KILLSWITCH — v8.24.0]`, una explicación de por qué se cortó (problema OS-level fuera del proceso), y la acción concreta para el humano (restart VS Code, verificar `%ComSpec%`, etc.); (4) yield `streamEnd`; (5) `return` del generator. CRÍTICO: no se ejecuta `messages.push(...)`, no se llama de nuevo al LLM, no se entra al circuit breaker, no se entra al telemetry log de improvements.md (irrelevante porque el problema no es de código). Detección por substring literal `[YIELD TO HUMAN` así cubre uniformemente: el payload de v8.16.8 (`[YIELD TO HUMAN — Node Environment Error]` para cmd.exe ENOENT), cualquier futuro tool que emita el mismo sentinel, y variantes con sufijos descriptivos. El precedente del v8.16.2 IO_CORE breaker (que también rompía el loop pero solo para 4 tools específicos en su path de circuit breaker) queda complementado, no reemplazado: ahora cualquier tool que llegue a emitir el sentinel — incluso fuera del breaker — corta el flujo financiero.
- **Strengthened Windows Spawn (`src/tools/RunCommandTool/index.ts`):** Refactor del shell selection para centralizar y hacer auditable la selección de terminal. Nueva utilidad top-level `resolveShellOption(): string | undefined` — única fuente de verdad para el `shell` option pasado a cada `execSync` del módulo. Implementación: `process.platform === 'win32' ? (process.env.ComSpec || process.env.COMSPEC || 'cmd.exe') : undefined`. Nota de tipo: el spec original pedía `shell: ... : true` para POSIX, pero el contrato tipado de `execSync` solo acepta `string | undefined` (la forma boolean `true` está documentada para `spawn`/`spawnSync`, no para `execSync`). Para honrar la INTENCIÓN del spec (forzar a Windows a localizar el terminal explícitamente para que un `%ComSpec%` vacío nunca termine en un spawn silencioso de la nada), Windows resuelve a un path concreto del shell y POSIX cae al `undefined` documentado por Node como "execSync usará `/bin/sh`". Cambia DOS call sites: (a) la rama del `git restore` allowlist (v8.16.13) que antes resolvía el shell inline; (b) la rama principal de `Execute` (v8.16.8) que también lo resolvía inline. Resultado: el behavior es platform-deterministic y el killswitch del motor puede confiar en un payload `[YIELD TO HUMAN]` clean y one-shot cuando el shell es genuinamente inalcanzable.
- **Broadened ENOENT detection (`src/tools/RunCommandTool/index.ts`):** El check `isShellMissing` ahora cubre `ENOENT`, `EPERM`, y `EACCES` (antes solo `ENOENT`), y el regex de mensajes acepta también `comspec` (case-insensitive) además de `cmd\.exe` / `spawnSync` / `system32`. Razón: en hosts Windows con políticas de seguridad lockdown (Defender restrictivo, AppLocker, GPOs corporativas), `cmd.exe` puede existir en disco pero ser inaccesible al child process spawneado — Node retorna `EPERM` o `EACCES` con un mensaje que menciona `comspec`. Antes esos errores se pasaban por la rama genérica de "command failed", el LLM intentaba retry, y el ciclo de panic se disparaba igual. Ahora también caen en la rama YIELD_TO_HUMAN y el killswitch del motor los corta.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.24.0`.
- **Resultado:** Cierra el primer modo de fallo financiero serio observado en sesiones reales. La cadena causal completa queda neutralizada en tres capas: (1) `RunCommandTool` detecta el shell loss y emite el sentinel `[YIELD TO HUMAN` con cobertura ENOENT+EPERM+EACCES; (2) `agentEngine` intercepta el sentinel ANTES de tocar `messages` o llamar al LLM y termina el generator limpiamente; (3) el usuario ve un mensaje único y accionable en la UI explicando qué pasó y qué hacer. Costo del fallo: bajado de "$1.50 + 25 iteraciones quemadas + frustración" a "0 API calls + 1 mensaje claro al humano". Phase 4 (mutex + DAG conflict resolution), Phase 3 (RBAC + MCP registry), v8.21.0 cognitive strictness, v8.22.0 path sanitizer, v8.23.0 LSP passive feedback, v8.23.1 safe compaction — todo intacto. ## [v8.23.1] - The Safe Compaction Patch

**Objetivo:** Hotfix crítico para v8.22.0/v8.23.0. El Micro-Condenser introducido en v8.22.0 (`compactToolFailures`) y el Active Auto-Condenser de v8.23.0 (`proactiveCompact`) ambos removían mensajes del array vía `Array.splice` y, en el caso de v8.23.0, también insertaban un mensaje `role: 'system'` en su lugar. Esto violaba el contrato API de OpenAI/OpenRouter Chat Completions: cada `tool_call` emitido por un assistant message DEBE estar seguido por un `role: 'tool'` message con el `tool_call_id` correspondiente — la regla es estricta, 1-to-1, sin huecos. Al splicear un tool result, el `tool_call` previo del assistant quedaba huérfano y el siguiente request fallaba con `HTTP 400: An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`. Síntoma observable: la primera vez que el Circuit Breaker disparaba (v8.22.0) o que el active condenser detectaba >24 mensajes con residue (v8.23.0), la siguiente llamada al LLM crasheaba con 400 y el turno se rompía. v8.23.1 reescribe ambas rutinas para usar **mutación in-place del payload** en vez de `splice` — el array length nunca cambia, ningún mensaje se mueve de índice, ningún mensaje se inserta o borra. Solo el `content` string de los mensajes target se reescribe a un stub corto. Mismo ahorro de tokens, cero ruptura de schema.

- **Safe Mutation contract (`src/utils/condenser.ts`):** Reescritura completa de las dos funciones bajo una regla de hierro documentada al tope del archivo: _"The ONLY message array length changes legal in this file are: zero. The array length on exit always equals the array length on entry."_ Nuevos helpers privados `buildReactiveSummary(toolName, count)` y `buildActiveSummary(failures, redundantEdits, failingTools, files)` que construyen los strings de summary verbosos, más dos constantes `REACTIVE_STUB_SHORT = '[CONDENSER] Tool output compressed to save tokens.'` y `ACTIVE_STUB_SHORT = '[COMPACTED MEMORY] Tool output compressed to save tokens.'` para los mensajes secundarios.
- **`compactToolFailures` rewrite:** Identifica los target indices igual que antes (walk back, skip already-condensed por idempotencia, cap N). En vez del bloque `messages.splice(idx, 1) ... messages.splice(earliest, 0, condenserMessage)`, ahora hace un solo loop: para cada índice mutate `messages[idx].content` directamente — el ÍNDICE más pequeño (earliest) recibe el `buildReactiveSummary(toolName, N)` (con counts y la directiva "MANDATORY: change strategy"), todos los otros reciben el `REACTIVE_STUB_SHORT` de una línea. La envoltura estructural (role='tool', name, tool_call_id) queda intacta — el pairing API se preserva 100%. `insertedAt` ahora reporta el índice mutado más temprano (no insertado, porque ya nada se inserta).
- **`proactiveCompact` rewrite:** Mismo principio. Pass 1 colecta `failureIndices` y `redundantEditIndices` igual que antes (walking back, skip `[COMPACTED MEMORY]` y `[CONDENSER]` por idempotencia, dedup por `(tool, path)` para edits superseded). Pass 2 ahora hace `allIndices = [...failureIndices, ...redundantEditIndices].sort((a, b) => a - b)` (orden ascendente para identificar el earliest = `allIndices[0]`), y luego itera mutando `m.content` in-place: `idx === earliest` → `buildActiveSummary(...)` (con counts + tools + affected files), resto → `ACTIVE_STUB_SHORT`. La operación `splice` se elimina por completo — no hay un solo `messages.splice(...)` en el archivo entero después de este patch.
- **Idempotencia preservada:** Los stubs comienzan con `[CONDENSER]` o `[COMPACTED MEMORY]` así los checks `startsWith('[CONDENSER]')` y `startsWith('[COMPACTED MEMORY]')` al inicio del walk siguen funcionando — re-runs no re-mutan mensajes ya compactados. Y como `isFailureContent` solo matchea contra `FAILURE_PREFIXES` (que NO incluye los stubs), un mensaje ya compactado no será re-targeteado por el detector de failures en una pasada posterior. Los dos condensers (reactive + active) siguen no-colisionando vía sus prefijos exclusivos.
- **`write_file` añadido al EDIT_TOOLS set del proactive condenser:** Pequeña mejora ortogonal al hotfix — `write_file` no estaba en el set de v8.23.0, lo que dejaba escapar los redundant writes del mismo archivo a través del compactor activo. Ahora también se considera para dedup `(tool, path)`.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.23.1`.
- **Resultado:** Cierra el bug API 400. El test path es directo: si el Circuit Breaker dispara para `search_and_replace` después de 2 fallos consecutivos, `compactToolFailures` mutará in-place los 2 fallos previos sin tocar la longitud del array → la siguiente llamada al LLM contiene exactamente la misma estructura de assistant→tool pairings → no hay 400. Mismo razonamiento para `proactiveCompact` en sesiones >24 mensajes. Las garantías cognitivas de v8.22.0/v8.23.0 (compresión de payload, prevención de Context Window Intoxication) se mantienen intactas — solo el método de aplicación cambia. Phase 4 (mutexes + DAG conflict auto-resolution), Phase 3 (RBAC + MCP registry), Phase 1 cognitive strictness (v8.21.0) — todo intacto. ## [v8.21.0] - The Cognitive Strictness Patch

**Objetivo:** Phase 4 tools y LSP injections funcionan, los builds salen verdes, pero el LLM seguía pegándose contra el techo de 25 iteraciones por dos razones humanas-pero-fatales: (1) **Verification Anxiety** — después de un `replace_symbol` exitoso seguido de un `npm run build` con exit code 0, el agente no se fiaba de los dos oráculos independientes (LSP + compilador) y entraba en un loop de `grep` / `read_file` "para confirmar que el código realmente se escribió", quemando iteraciones hasta colgarse; (2) **Path Hallucination en terminal** — bajo presión de recovery, el coder hallucinaba `cd .fluxo/worktrees/<id>` para "navegar" a su propio worktree, lo que rompía el cwd (path doblemente anidado) y disparaba la cadena de retries que también consumía iteraciones. v8.18.1 ya había blindado las hallucinations Windows-absolute en `read_file`/`get_code_structure`; esta versión cierra los dos huecos restantes con una directiva mental dura en el system prompt + un shield físico al frente del runner de comandos.

- **Anti-Verification Loop Rule (`src/agents.ts` — `@coder` system prompt):** Nuevo bloque `━━━ VERIFICATION STRICTNESS (v8.21.0 — NON-NEGOTIABLE) ━━━` inyectado entre el `BUILD REPAIR PROTOCOL` (v8.16.11) y el `QUALITY GATE RULE` (v8.16.0). IMMEDIATELY call 'exit_worktree(action='merge')' to end your turn."_ El bloque va acompañado de la justificación (dos oráculos independientes — LSP + compiler — confirman el edit; no hay tercer oráculo que valga las iteraciones) y de la consecuencia operacional (cada post-green grep/read consume una iteración hacia el ceiling de 25 y arriesga un deadlock de turno). Posicionado intencionalmente DESPUÉS de `BUILD REPAIR PROTOCOL` para que el agente lea primero "qué hacer si el build falla" y luego "qué hacer cuando el build pasa" — la secuencia narrativa refuerza que los dos caminos son distintos y que el camino verde tiene una salida única (merge, no re-verify).

Use relative paths from the root of your current sandbox."_ El shield es complementario al `WORKTREE NOTE` que ya vivía en la `description` del tool desde v8.16.7 (capa prompt) — ahora hay redundancia prompt + física, igual al patrón que v8.17.4 estableció para git checkout/merge.

## [v8.20.0] - The Seamless UX & MCP Registry Patch

**Objetivo:** v8.19.0 cerró Phase 3 a nivel arquitectónico — RBAC + categorías + JSON workspace-scoped — pero la DX seguía rota: el usuario tenía que abrir un editor, googlear el comando exacto de cada MCP server, escribir JSON a mano, recordar el shape, y rezar para no romper la sintaxis. - **Official Default Registry (`src/utils/mcpRegistry.ts` — NEW):** Catálogo built-in de MCP servers conocidos. Cada entrada es un `RegistryEntry` con `alias` (el string corto que el usuario tipea), `description` (one-liner para pickers), `command` + `args` (executable + flags), `env` opcional (con placeholders `${ENV:NAME}` para secrets), `categories` (alimentadas directo al RBAC filter de v8.19.0), `starter: true|false` (true = se incluye en el auto-pack de primer arranque), y `note` (texto humano que se renderiza en el JSON como sidecar para ayudar al usuario a entender qué editar). - **MCP Config Writer (`src/utils/mcpConfigWriter.ts` — NEW):** Capa única de I/O sobre `.fluxo/mcp_servers.json`. - **Zero-Config Auto-Injection (`src/mcpClient.ts`):** En `_loadMergedConfig`, ANTES de leer el JSON workspace, se llama `ensureStarterPack(workspacePath)`. La idempotencia es crítica: en arranques subsecuentes, el archivo existe → no se re-escribe nada → la elección del usuario (que pudo haber removido o agregado servers) se respeta. Si el usuario lo borra deliberadamente, el siguiente arranque lo regenera con el pack default — esto es intencional, mejor un default sano que ningún MCP. La variante "deliberadamente vacío" se logra dejando un JSON con `mcpServers: {}` (existencia del archivo cuenta, content vacío gana).
- **Graceful npx -y handling (`src/mcpClient.ts`):** Tres mejoras al boot path para evitar hangs con MCPs vía `npx -y`. (1) **Connect timeout bumped 5s → 30s** — `npx -y @modelcontextprotocol/server-X` en cache fría puede tardar 10-30s descargando el package; 5s era demasiado agresivo y abortaba la primera ejecución cada vez. 30s da headroom sin colgar la sesión indefinidamente. (2) **Parallel boot via `Promise.allSettled`** — antes los servers se conectaban serialmente (un loop `for ... await`), así N servers lentos sumaban latencia linealmente. (3) **Transport cleanup on timeout** — cuando el connect race pierde contra el timeout, ahora se llama `transport.close()` explícitamente para no dejar procesos `node` huérfanos sosteniendo pipes stdio. Antes, el child process quedaba dangling hasta que el extension host moría.

- **Interactive CLI Commands (`src/commands/mcp.ts` — NEW):** Standalone Node entrypoint que mirrorea el patrón de `claude mcp add`. Compilado a `out/commands/mcp.js`. Subcomandos: `add <alias> [--workspace=<path>]` (resuelve alias contra registry, llama `addServer`), `remove <alias>` / `rm <alias>` (llama `removeServer`), `list` / `ls` (renderea servers configurados con su comando completo + categorías), `registry` (lista todas las entradas oficiales con descripción + categorías + note + marca `★` en starters). Self-contained: import gates (`if (require.main === module)`) permiten que el módulo también se importe desde código sin ejecutar el entrypoint. Invocable como `node out/commands/mcp.js <subcommand>` o, si el repo está en PATH via npm link, como `fluxo mcp <subcommand>`.
- **VSCode Command Surface (`src/extension.ts` + `package.json`):** Tres comandos nuevos registrados en el command palette y contribuidos en `package.json` `contributes.commands`: (1) **`fluxo.mcp.add`** ("Fluxo: Add MCP Server", ícono `$(plug)`) — quickPick que muestra TODAS las entradas del registry con marca `★` para starters, descripción + categorías como subtítulo. Las tres comparten el mismo writer (`mcpConfigWriter`) que el CLI, así no hay drift entre los dos surfaces.

## [v8.18.1] - The Pathing & DAG Injection Patch

**Objetivo:** Hotfix para Phase 4. v8.18.0 entró en dogfooding y dos bugs críticos saltaron: (1) el mutex secuencial atrapaba el merge conflict correctamente y disparaba el catch path, pero `dagController.appendTask` retornaba `null` — el task de auto-resolución NO se inyectaba en el DAG, así que la cadena de recovery se rompía silenciosamente. La causa raíz: el `workspacePath` que ExitWorktreeTool recibía resolvía a un directorio que no contenía `.fluxo/dag_state.json` (relacionado con el contexto de worktree activo), así que `read()` dentro de `appendTask` no encontraba el archivo y devolvía null. (2) El @coder bajo presión de recovery hallucinó paths absolutos de Windows del estilo `C:/Users/erick/source/repos/...` cuando llamaba `read_file` y `get_code_structure` — paths que apuntaban literalmente a un repo del usuario que NO era el workspace activo, causando ENOENT y rompiendo el resto de la sesión. Esta versión cierra ambos bugs con dos fixes muy quirúrgicos.

- **Global DAG Injection Fix (`src/tools/ExitWorktreeTool/index.ts`):** Nueva utilidad `resolveRepoRoot(cwdPath)` interna al tool — corre `git rev-parse --show-toplevel` con `stdio: ['pipe', 'pipe', 'ignore']` (descarta stderr para no ensuciar logs) desde el cwd que recibió el tool, y devuelve la ruta canónica absoluta del repositorio. `git rev-parse --show-toplevel` es la API oficial de git para resolver el root del repo desde cualquier subdirectorio, incluyendo worktrees secundarios — exactamente lo que necesitamos. En el catch path del merge conflict, ANTES de llamar `getCurrentInProgressTask` y `appendTask`, se computa `const repoRoot = resolveRepoRoot(workspacePath)` y SE USA `repoRoot` como argumento en ambas llamadas (en vez del `workspacePath` recibido). Esto garantiza que las DAG ops siempre lean/escriban `.fluxo/dag_state.json` en el root real del proyecto, sin importar si el `workspacePath` recibido apuntaba a un worktree, una subcarpeta, o un mount-point inusual. Fallback defensivo: si `git rev-parse` falla (p.ej. cwd no es un repo), `resolveRepoRoot` retorna el `cwdPath` original — comportamiento idéntico al previo en el caso degenerado, sin romper nada.
- **Absolute Path Hallucination Blocker (`src/tools/shared.ts` + `src/tools/FileReadTool/index.ts` + `src/tools/GetCodeStructureTool/index.ts` + `src/agentEngine.ts`):** Nuevo helper compartido `rejectIfAbsolutePath(rawPath)` en `shared.ts` — regex `/^(?:[A-Za-z]:[\\/]|\/)/` matchea cualquier path que empiece con drive letter Windows (`C:/`, `D:\`) o leading slash POSIX (`/home/...`). Si match, retorna un `ToolResult` con el mensaje verbatim solicitado: _"[SYSTEM SHIELD] Absolute paths are strictly forbidden. You MUST use relative paths from the repository root (e.g., 'src/components/App.jsx')."_ Si el path es relativo (o vacío/no-string), retorna `null` y el tool sigue su flujo normal. Wired en tres puntos:
  1. **`FileReadTool.execute()`:** primer statement del execute, antes de `safePath()` y antes del `fs.existsSync` — la rejection ocurre antes de tocar disco. El @coder ya no puede llamar `read_file({path: "C:/Users/erick/..."})` y obtener un misleading "FILE NOT FOUND" (que antes lo mandaba a un loop de `list_dir` infructuosos).
  2. **`GetCodeStructureTool.execute()`:** mismo guard al frente. Notar que en producción este `execute()` casi nunca corre (el agentEngine intercepta `get_code_structure` y llama directo al callback de VS Code), pero se mantiene por defense-in-depth y para que la rejection sea uniforme si el intercept se desactiva. El parámetro sigue llamándose `absolute_path` por compatibilidad con el contexto histórico del LLM, pero la descripción se actualizó para clarificar: _"Path to the file relative to the workspace root... drive-letter and root-slash absolute paths are blocked."_
  3. **`agentEngine.ts` get_code_structure intercept:** mismo regex inline (no se importa el helper desde el tool para no introducir un import circular tools→engine), aplicado al `args.absolute_path` ANTES de llamar `getCodeStructureCallback`. Si el regex matchea, asigna `result = {success:false, output: '[SYSTEM SHIELD] ...'}` con el mensaje verbatim, salta el yield del `'thinking'` y el callback nunca se invoca. Esta es la capa que físicamente bloquea las hallucinations en producción.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.18.1`.
- **Resultado:** Cierra los dos bugs blockers de Phase 4. La cadena de recovery del conflict resolver ahora ejecuta end-to-end: mutex protege el merge → conflict ocurre → catch captura → cleanup atómico → DAG injection EXITOSA (vía repo root canónico) → dispatcher de Phase 2 ve el task nuevo en el siguiente tick y spawnea al @coder. Y los path hallucinations Windows-absolute quedan rejected en la misma capa que ya bloquea grep/glob para agentes sin panoramic view (Physical Shield v8.17.4) — el agente no puede saltarse al filesystem real del usuario por accidente.

## [v8.18.0] - Phase 4: Deferred Mutexes & Conflict Resolution

**Objetivo:** Saltarse Phase 3 (MCP) y atacar directamente el problema más caro del Phase 2: en pruebas de ejecución paralela del DAG, varios sub-agentes spawneados por el dispatcher (v8.17.2) intentaban hacer `exit_worktree(merge)` simultáneamente sobre el mismo `main`, generando race conditions a nivel del git index. v8.17.4 (Physical Enforcement) parchó el síntoma — auto-discard del worktree en colisión + cleanup atómico — pero el resultado neto era que TODA la work del task fallido se perdía: el dispatcher marcaba el task como FAILED, el @manager veía la falla, y el ciclo se quedaba ahí. Cero recovery automático, tokens quemados sin output. Phase 4 agrega dos capas: serialización determinística de los merges (mutex secuencial) + auto-recovery dinámico via inyección de tasks de alta prioridad en el DAG (el sistema arregla su propio conflict en el siguiente tick del dispatcher).

- **Sequential Merge Mutex (`src/utils/gitSafety.ts`):** Nueva utilidad `acquireMergeMutex(workspacePath, holderId)` + `MergeMutexHandle.release()`. Lock cross-process basado en archivo: `.fluxo/merge.lock` creado atómicamente con `fs.openSync(..., 'wx')` (flag exclusivo — falla limpio con EEXIST si ya existe). Si está locked, busy-wait con `Atomics.wait` (NO spin-burning de CPU — bloquea el event loop como si fuera execSync) en intervalos de `MERGE_LOCK_POLL_MS=100ms` hasta `MERGE_LOCK_TIMEOUT=30000ms`. Detección de stale locks via mtime — un lock con más de `MERGE_LOCK_STALE_MS=60000ms` se considera huérfano (proceso que crashed sin release) y se fuerza la limpieza. Payload del lock incluye `holder`, `pid`, `acquired_at` para diagnóstico. Razón de elegir lock de archivo en vez de mutex en memoria: cubre el caso de múltiples ventanas de VS Code abiertas sobre el MISMO repo (cada una con su propia instancia de Fluxo AI) — el lock de archivo es la única forma de coordinar entre procesos de Node distintos. Y dentro de un solo proceso, sigue siendo correcto (la wx flag es atómica a nivel filesystem syscall).
- **Mutex wired al merge step (`src/tools/ExitWorktreeTool/index.ts`):** `acquireMergeMutex` se llama ANTES del primer `git merge` en el Step 2; si retorna `null` (timeout de 30s), se devuelve un error temprano explicando que otro agente está mergeando — el agente puede reintentar después. La sección crítica (merge attempt → catch → cleanup → DAG injection) corre bajo el lock; release explícito en el catch path antes de tocar el DAG (mantenemos la sección crítica corta), y release defensivo en el `finally` (idempotente — el unlink interno catch silencia el error si el archivo ya está borrado). Si el merge sucede limpio, el `finally` libera; si falla, el catch libera antes de la inyección DAG.
- **DAG Conflict Auto-Resolution (`src/tools/ExitWorktreeTool/index.ts` + `src/utils/dagController.ts`):** Cuando el merge falla, antes del `git merge --abort` el motor captura el contexto del conflict (la única ventana en la que los markers `<<<<<<< HEAD` están vivos en `main`): `git diff --name-only --diff-filter=U` extrae la lista de archivos en conflicto, y para cada uno (cap 6) se lee el primer bloque `<<<<<<<` (cap 1500 chars) via `fs.readFileSync`. DESPUÉS el motor hace todo el cleanup atómico de v8.17.4 (abort + worktree remove --force + prune + branch -D + state file unlink). Después, `dagController.appendTask` inyecta un task nuevo con `idPrefix: 'conflict'` (el id queda `conflict-N` donde N es el siguiente disponible), `agent_type: '@coder'`, descripción que combina título urgente + identidad del task fallido (capturada via `getCurrentInProgressTask`) + protocolo de resolución de 7 pasos + los snippets de conflict capturados + el stderr crudo de git. La descripción es lo que el dispatcher (Phase 2) usa como prompt cuando spawna al @coder en el siguiente tick. Tool returns: `[MERGE CONFLICT] A collision occurred. A priority conflict-resolution task has been queued in the DAG. Exit your turn immediately.` (texto verbatim solicitado) + nota sobre cuál es el id del nuevo task y a qué parent se vincula.
- **Nuevas APIs en dagController (`src/utils/dagController.ts`):** Dos helpers nuevos para soportar la inyección dinámica. `appendTask(workspacePath, {description, agent_type, depends_on?, idPrefix?})` lee el DAG vivo, genera un id único con sufijo numérico que evita colisiones con tasks existentes, persiste el task nuevo con `status: 'PENDING'`, y devuelve el `Task` insertado o `null` si no hay DAG activo. `getCurrentInProgressTask(workspacePath)` devuelve el task con status `IN_PROGRESS` más recientemente iniciado (sort por `started_at` descendente) — usado por ExitWorktreeTool para identificar quién es el "parent" semántico del conflict.
- **Nota de diseño — depends_on intencionalmente vacío:** El user spec pidió que el conflict task "must depend on the failed task". La implementación honra el linkage causal pero NO via `depends_on`, porque la lógica de `getReadyTasks` sólo desbloquea PENDING tasks cuyas dependencias están en COMPLETED — y el parent acaba marcado FAILED por el lifecycle hook del dispatcher segundos después de que este tool retorna. Si pusiéramos el parent en `depends_on`, el conflict task se quedaría en PENDING forever. La trazabilidad al parent vive en la descripción ("Parent task: <id> (<description>)..."), donde es visible para el @coder cuando lo spawnean Y para auditoría humana cuando se mira el JSON. La semántica efectiva: el conflict task es root (depends_on: []) → unblocked en el siguiente tick → dispatcher lo agarra → @coder lo ejecuta → resuelve sin worktree (la descripción explícitamente dice "do NOT enter a worktree for this task") → marca COMPLETED. La cadena causal queda en el DAG como un grafo no-bloqueante donde el conflict-N "sigue" al task fallido pero no lo espera.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.18.0`.
- **Resultado:** Cierra Phase 4. Los race conditions a nivel git index quedan eliminados — los merges concurrentes se queuean atómicamente. Y cuando un conflict ocurre, en vez de perder todo el trabajo del task, el motor genera dinámicamente un task de recovery con TODO el contexto necesario (lista de archivos, snippets de markers, stderr de git, protocolo de resolución), lo inyecta en el DAG, y el dispatcher de Phase 2 lo recoge sin que el @manager tenga que reaccionar manualmente. El sistema se auto-arregla. Phase 5 (probable: paralelismo de dispatch via `Promise.all` ahora que el mutex hace seguros los merges concurrentes) puede arrancar sobre esta base.

## [v8.17.4] - The Physical Enforcement Patch

**Objetivo:** Tres parches del Phase 2 (v8.17.1 → v8.17.3) introdujeron reglas cognitivas en los system prompts del @coder y @designer — RAW_GIT_WORKFLOW_BLOCK, PANORAMIC RULE, UDIFF-STYLE PRECISION. En dogfooding bajo presión de merge conflicts y context drift, el LLM las ignoraba sistemáticamente: arrancaba a editar archivos sin haber llamado `get_repo_map`, ejecutaba `git checkout master` por reflejo cuando una task fallaba, y entraba en pánico tratando de "resolver" conflicts manualmente con git crudo después de un `exit_worktree(merge)` fallido. Las reglas de prompt son sugerencias para un LLM bajo estrés. Esta versión las promueve a hard physical blocks en el motor y en los tools — el agente literalmente NO PUEDE ejecutar la acción prohibida, no importa cuántas veces lo intente. Última estabilización del Phase 2 antes de abrir el camino a MCP y Deferred Mutexes.

- **Panoramic Physical Shield (`src/agentEngine.ts`):** Nueva flag de sesión `hasSeenRepoMap = false` declarada al inicio de cada `runAgentLoop`, junto a `dispatchedReady`. Sets dedicados `PANORAMIC_GATED_AGENTS = {coder, designer}` y `PANORAMIC_GATED_TOOLS = {grep, glob, search_in_files, search_and_replace}`. Nuevo guard insertado en el loop de ejecución de tools, ANTES del Rabbit Hole Block (v8.16.23) — así el shield message llega al LLM aunque también haya intentado grep en `node_modules`. Lógica: si `agentId ∈ PANORAMIC_GATED_AGENTS` Y `toolName ∈ PANORAMIC_GATED_TOOLS` Y `!hasSeenRepoMap`, yield `toolResult` con `success: false` + el mensaje exacto solicitado: _"[SYSTEM SHIELD] You are operating blind. You MUST call get_repo_map to gain spatial awareness before searching or editing."_ Push como `tool` content al historial y `continue` — la call jamás llega a `executeTool`. La flag se levanta en una sola condición: `toolName === 'get_repo_map'` Y `result.success === true` Y `!hasSeenRepoMap`. Una vez levantada, los tools gated ejecutan normalmente para el resto de la sesión. Razón del scope estricto a coder/designer: el @manager y el @planner tienen otros paths de lectura (RepoMap auto-inyectado en system prompt para manager, read-only mission para planner) — gatearlos generaría falsos positivos.
- **Raw Git Tool-Level Block (`src/tools/RunCommandTool/index.ts`):** El `RAW_GIT_WORKFLOW_BLOCK` (v8.17.1) era una directiva de prompt que el LLM bypaseaba bajo presión. Promovido a un block físico en el ejecutor de `run_command` mismo. Insertado justo después del `GIT_RESTORE_ALLOW` short-circuit (así `git restore <path>` sigue funcionando como CTRL+Z) y antes del Vite Panic Blocker. Lógica: `RAW_GIT_BLOCK_PATTERN = /^\s*git\s+(checkout|merge)\b/i` aplicado a CADA segmento del comando split por `|`, `;`, `&` (previene evasión via `git status; git checkout master`). Allowlist defensiva: `MERGE_ABORT_ALLOW = /^\s*git\s+merge\s+--abort\b/i` — `git merge --abort` es un recovery path, no una operación de branching, debe pasar limpio. Si match: return literal `[SYSTEM BLOCK] Raw git branching/merging is physically disabled. Use exit_worktree.` (texto verbatim del usuario). El comando jamás llega a `execSync`. Cubre: `git checkout master`, `git checkout -b foo`, `git merge feature/x`, y todas las variantes con flags. NO bloquea: `git restore`, `git status`, `git log`, `git diff`, `git fetch`, `git pull`, `git push` (push se queda en la layer de prompt v8.17.1, fuera del scope de este patch).
- **Auto-Discard on Conflict (`src/tools/ExitWorktreeTool/index.ts`):** v8.17.3 hacía `git merge --abort` en fallo de merge y dejaba al agente con la instrucción de "discard the worktree and report to manager". En dogfooding el @coder NO discarteaba — entraba en pánico, intentaba `git status` para "ver qué pasó", luego `git diff`, después intentaba editar los archivos en conflict directamente, quemaba 5-10 iteraciones. v8.17.4 quita la elección al agente: el motor ejecuta atomicmente el cleanup completo dentro del catch — `git merge --abort` (limpia MERGING state) → `git worktree remove --force` → `git worktree prune` → `git branch -D <branchName>` → `fs.unlinkSync` del state file. Cada paso wrapped en try/catch independiente para que el cleanup nunca falle parcial. Return string actualizado al texto exacto solicitado: _"[MERGE CONFLICT] Codebase collision detected. The worktree was automatically discarded by the engine. End your turn immediately so the Manager can reschedule this task."_ + el primer trozo de stderr para diagnóstico. El @coder ya no tiene un worktree que discartear — el motor lo hizo. Sólo le queda la única acción legal: cerrar el turno y devolver el control al @manager (que en Phase 2 ya tiene el lifecycle hook que mapea esta failure a `FAILED` en el DAG).
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.17.4`.
- **Resultado:** Cierra el desliz cognitivo del Phase 2. Las tres reglas más violadas en dogfooding (panoramic-first, no raw git, no manual conflict resolution) ahora viven en código del motor, no en texto de prompt. El LLM puede seguir intentando — no va a poder. La sesión se mantiene en un estado coherente independientemente de cuánto el LLM derive bajo presión. Phase 3 (MCP + Deferred Mutexes) puede arrancar sobre una base estable.

## [v8.17.3] - The Panoramic AST & Conflict Patch

**Objetivo:** Phase 2 (v8.17.2) entró en dogfooding y reveló dos modos de fallo costosos en token: (1) los sub-agentes spawneados por el dispatcher entraban a editar archivos sin haberlos visto antes — el LLM "recordaba" la estructura de su entrenamiento, alucinaba imports, y quemaba ciclos en MATCH ERRORS y grep loops para triangular código que el motor le podría haber dado en una sola call; (2) cuando dos tasks paralelas tocaban regiones cercanas y el merge de uno fallaba por colisión, el `exit_worktree(merge)` dejaba el workspace principal en estado MERGING dirty — los conflict markers `<<<<<<<` se filtraban a `git status`, todos los siguientes comandos git de la sesión devolvían errores incoherentes, y el agente entraba en pánico intentando "arreglar" el conflict manualmente. Esta versión adopta el paradigma Aider: visibilidad estructural panorámica antes de tocar código + auto-recovery atómico cuando la integración falla.

- **Panoramic RepoMap (`src/utils/repoMap.ts` + `src/tools/GetRepoMapTool/index.ts`):** El RepoMap existente (v8.12.0) extraía sólo signatures TS/JS via AST y devolvía un flat list. v8.17.3 lo expande a una vista panorámica de dos niveles: (1) un **directory tree** indentado (depth ≤ 6) en el header del output, con un sufijo `(N)` indicando cuántos símbolos top-level tiene cada archivo — la primera mirada le da al agente la topología completa sin scrollear; (2) los **per-file symbol blocks** detallados debajo. Polyglot fallback nuevo via regex para `.py`, `.go`, `.rs`, `.java`, `.rb`, `.cs`, `.php`, `.kt`, `.swift` — cada lenguaje tiene un par de regexes (functions + classes/structs/traits) que extraen los nombres top-level. Aider-style: incluso un set aproximado de símbolos le da al agente suficiente estructura para elegir el archivo correcto antes de leerlo. Stable sort en `scanDir` (directorios primero, luego archivos, ambos alfabéticos) para que el tree no se reordene entre llamadas. Hard caps: `MAX_TREE_ENTRIES=250`, `MAX_TREE_DEPTH=6`, `MAX_REPO_MAP_CHARS=15000` mantenidos. La descripción del tool fue reescrita para enfatizar el carácter MANDATORY del paradigma — explícito sobre los modos de fallo (MATCH ERRORS, ghost imports, grep loops) que el panorama previene.
- **PANORAMIC RULE (v8.17.3 — NON-NEGOTIABLE) en el @coder (`src/agents.ts`):** Reemplaza la TOPOGRAPHY RULE (v8.12.0) — el block antiguo era un párrafo recomendatorio que el LLM podía interpretar como sugerencia. La nueva versión es un block delimitado con `━━━`, marcado NON-NEGOTIABLE, y con la directiva exacta solicitada: _"Before modifying any unknown file, you MUST use get_repo_map to gain a panoramic view of the codebase structure."_ Define "known file" = "uno que ya leíste en esta sesión", lista los modos de fallo concretos que el shortcut causa (MATCH ERRORS, ghost imports, grep loops), y cierra declarando que supersede la regla legacy. Aplica al @coder; el @manager y @designer también heredan get_repo_map en su toolset así que la disciplina se propaga naturalmente cuando el dispatcher (v8.17.2) los spawnea.
- **Merge Conflict Auto-Abort (`src/tools/ExitWorktreeTool/index.ts`):** El merge step (Step 2) ahora envuelve el catch del `git merge` con un `git merge --abort` automático. Si el merge tira (cualquier error — usualmente conflict, pero también unrelated histories, etc.), inmediatamente intenta abortar; si el abort funciona, anota `(git merge --abort succeeded — workspace restored to pre-merge state)`; si no había MERGING activo (e.g. el merge falló por otra razón antes de entrar al estado), anota `(no MERGING state to abort)`. El return retorna el mensaje literal solicitado por el usuario: `[MERGE CONFLICT] The merge failed due to codebase collisions. The merge was cleanly aborted...`. Razón del diseño: el agente NO tiene una vía confiable de resolver conflicts mid-loop (requiere edición manual con context que él no tiene), y el estado MERGING dirty contamina TODA la sesión — `git status`, `git diff`, los hooks de checkpoint y rollback, todo se rompe. Auto-abort + directive única ("discard + report to manager") elimina la contaminación al instante y le da al sub-agente exactamente UN camino legal de salida.
- **udiff-Style Precision en SearchReplaceTool (`src/tools/SearchReplaceTool/index.ts`):** Nueva sección `⚠️ UDIFF-STYLE PRECISION (v8.17.3)` añadida al frente de la descripción del tool, antes del STRATEGY existente. Cuatro reglas hard-numbered: (1) ALWAYS read_file antes — leer de memoria de un turno previo está PROHIBIDO porque los archivos mutan; (2) copiar el search_snippet VERBATIM, character por character, sin retipear; (3) formatear el replace_snippet como un hunk udiff — misma indentación, mismo line-ending style, sin trailing whitespace; (4) si el call previo retornó MATCH ERROR, NO retry con guess — re-leer y copiar verbatim de nuevo. El WORKFLOW existente recibió un anchor "(MANDATORY — see UDIFF rule above)" en el step 1 para que el LLM no separe la regla del flujo. La fuzzy matching del motor sigue intacta (es la safety net), pero el copy ahora aclara explícitamente que fuzzy NO es una licencia para improvisar indentación.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.17.3`.
- **Resultado:** Cierra los dos modos de fallo del Phase 2 dogfooding. El paradigma Aider entra al @coder por dos puertas — visibilidad estructural mandatoria antes de cualquier edit (panoramic rule) + precisión udiff en el tool de edits surgical (search_and_replace). Y la red de seguridad de integración: cualquier merge fallido limpia su propio dirty state y deja al sub-agente con UN único next action en vez de un workspace corrupto. El token burn observado en pruebas debería caer significativamente — Phase 4 medirá el impacto en una sesión multi-task con dependencias cruzadas.

## [v8.17.2] - The Active Dispatcher

**Objetivo:** Phase 2 del DAG Orchestrator. Phase 1 (v8.17.0) entregó un observer pasivo que sólo loggeaba qué tareas estaban "ready"; el @manager seguía siendo el cuello de botella cognitivo — tenía que leer el log, decidir a quién delegar, llamar `create_team` manualmente, y tracker el estado a mano. v8.17.1 cerró los blockers de filesystem y workflow; ahora el motor por sí mismo lee el grafo, dispara los sub-agentes correctos, y cierra el ciclo de vida (COMPLETED/FAILED) al volver. El @manager pasa de orquestador-operador a orquestador-supervisor.

- **Active Task Delegation (`src/agentEngine.ts`):** El bloque pasivo `[DAG Engine] Task <id> is unblocked and ready` (Phase 1) fue reescrito a un dispatcher activo que ejecuta CINCO pasos por cada task `getReadyTasks` devuelve: (1) normalización del `agent_type` — strip de `@` inicial + lowercase, fallback a `coder` si el nombre no matchea ningún agente conocido, así un typo no estranda la task; (2) guard de auto-targeting — `targetAgentId === 'manager'` se rechaza con `FAILED` antes del spawn (un manager dispatchando a sí mismo colapsaría el loop en recursión infinita); (3) flip atómico a `IN_PROGRESS` vía `dagController.updateTaskStatus` ANTES de spawnear, así si el siguiente tick re-evalúa, `getReadyTasks` ya no devuelve esa task como PENDING y previene doble-dispatch; (4) construcción dinámica del prompt con tag `[DAG TASK <id>]` + descripción + contrato de cierre; (5) llamada a `runAgentLoop` recursiva con la lista completa de callbacks (approval, native edit, code structure, MCP, worktree review, replace symbol, HITL — todos propagados para que el sub-agente tenga la misma capacidad operativa que el manager).
- **Gate `agentId === 'manager'` — sólo el orquestador dispatcha (`src/agentEngine.ts`):** El dispatcher se ejecuta exclusivamente cuando `agentId === 'manager'`. Razón: cada `runAgentLoop` (incluyendo el sub-agente spawneado) entra al mismo while loop, y sin este gate cada @coder spawneado intentaría re-evaluar el DAG y disparar otra ronda — cascade de recursión infinita. Como el @manager es el dueño del DAG (es quien llama `propose_plan`), centralizar el dispatch en él es la frontera natural.
- **Lifecycle Hooks — COMPLETED / FAILED (`src/agentEngine.ts`):** Después de drenar el async generator del sub-agente, el dispatcher inspecciona los eventos buffereados para derivar el outcome. `hadError = events.some(e => e.type === 'error')` captura todas las salidas no-limpias (Sherlock audit failure, API error, abort por usuario, crash de tool). `hitMaxIter = events.some(e => e.type === 'streamChunk' && e.text.includes('Reached maximum iterations'))` captura el sub-agente atascado en loop infinito (warning emitido por el propio MAX_ITERATIONS guard del motor). Si cualquiera dispara → `updateTaskStatus(taskId, 'FAILED', finalText)`. Caso contrario → `COMPLETED`. La justificación de la simetría con el Quality Gate: el motor YA bloquea el `streamEnd` salvo que el build esté verde (v8.16.0/8.16.1) y el merge se hizo (v8.16.17), así que un clean exit es prueba de QG passed + merge done — exactamente la condición que el usuario pidió que el dispatcher detecte.
- **Result harvest — el output del sub-agente se persiste en el DAG (`src/dagController.ts` already supports it):** Los `streamChunk` events del sub-agente se concatenan en `finalText` (cap 4000 chars para no inflar el JSON), y se pasan como tercer argumento a `updateTaskStatus`. Persistido en `dag_state.json` bajo `tasks[i].result`, así el @manager puede revisar el reporte de cualquier task completada en ticks futuros sin re-correr al sub-agente.
- **Spawn try/catch + crash hook:** Si `runAgentLoop` lanza por sí mismo (no un evento error, sino una excepción no manejada), el catch wrapper convierte la excepción en `FAILED` con mensaje `Spawn error: <msg>`, loguea, y `continue`. El motor jamás puede caer por culpa del dispatcher.
- **Convergencia del ciclo — `continue` después de un round de dispatch:** Al final del bloque, si `ready.length > 0`, el motor hace `continue` para saltarse la API call del @manager y re-evaluar el DAG en el siguiente tick. Razón: las tasks recién completadas pueden haber desbloqueado nuevas downstream (su `depends_on` ahora se cumple), y queremos drenarlas en cascada antes de que el @manager gaste tokens "pensando". El @manager sólo entra a la rueda de pensamiento cuando el frontier está vacío — pasa de operador activo a supervisor cuya cognición se reserva para el reporte final.
- **UI versioning (`media/main.js`):** Welcome card title bumped a `v8.17.2`.
- **Resultado:** Cierra Phase 2. El @manager ya no escribe los `create_team` a mano — propone el grafo una vez con `propose_plan`, el usuario aprueba, y el motor ejecuta el DAG completo de forma autónoma: dispatch → spawn → harvest → status update → re-evaluate. Cada task tiene un audit trail completo en `dag_state.json` (status final + output del sub-agente). Phase 3 (próxima versión) abrirá el dispatch a paralelismo: en vez de spawnear las ready tasks una por una, lanzar todas las independientes con `Promise.all` para colapsar la latencia del grafo a la altura del path crítico.

## [v8.17.1] - The DAG State & Git Workflow Patch

**Objetivo:** Phase 1 del DAG Orchestrator (v8.17.0) entró en dogfooding y reveló tres patrones de fricción que cierran este patch: (1) los sub-agentes escribían `dag_state.json` dentro del worktree sandbox y el @manager polling en la raíz nunca veía las actualizaciones — el dispatcher se quedaba colgado anunciando tasks "ready" que ya estaban completas; (2) el @coder y el @designer empezaban a improvisar con `git checkout master` / `git merge` / `git push` vía `run_command`, peleando contra el motor de Worktree Isolation y dejando estados de merge corruptos; (3) el circuit breaker del `read_file` lockeaba al agente para el resto de la sesión tras 3 fallos seguidos — incluso después de que la causa original (un path mal escrito) ya no aplicara.

- **Global State Bypass extendido a `dag_state.json` (`src/agentEngine.ts`):** El bypass de v8.16.20 que forzaba `IMPLEMENTATION_PLAN.md` a la raíz aunque hubiera worktree activo ahora cubre también `dag_state.json` y `task_dag_state.json`. Nueva regex `/(?:^|\/)(?:task_)?dag_state\.json$/i` evalúa el path arg después del normalize, y la decisión de redirección consulta `_isGlobalStateFile = _isPlanFile || _isDagStateFile`. La razón: el DAG es un orchestrator file global — TODOS los agentes leen y escriben en el MISMO `.fluxo/dag_state.json`. Si el @coder marca su task como COMPLETED dentro del sandbox, el @manager nunca lee la transición y el dispatcher se queda esperando un evento que jamás llegará. Log dedicado `[DAG State Bypass v8.17.1]` para distinguirlo del Plan Bypass clásico.
- **Raw Git Workflow Block (`src/agents.ts`):** Nuevo bloque NON-NEGOTIABLE `RAW_GIT_WORKFLOW_BLOCK` agregado al pipeline de `buildAgentSystemPrompt`, inyectado únicamente en agentes que tienen `run_command` (preserva al @planner read-only de ruido inútil). Establece la prohibición exacta solicitada: _"You are STRICTLY FORBIDDEN from using the run_command tool to execute git checkout master, git merge, or git push. To merge your changes from an isolated worktree back to the main branch, you MUST ONLY use the exit_worktree tool."_ El bloque enumera comandos permitidos (status, log, diff, fetch, branch sin -d/-D, etc.), comandos prohibidos (checkout, switch, merge, rebase, push, reset --hard, branch -d/-D, worktree), y deja explícito el lifecycle único: `enter_worktree → exit_worktree(merge|discard)`. Omite archivos binarios por extensión. Reemplaza `grep`, `findstr`, y `rg` en `run_command`. Límite: 500 matches.

## [v8.5.1] - The Boundary Patch (LSP Mismatch Fix)

**Objetivo:** Corregir el "LSP Boundary Mismatch" donde el rango del símbolo devuelto por el Language Server excluye el keyword inicial (`const`/`let`/`async`). Cuando el LLM incluye ese keyword en `new_code` y el engine aplica el reemplazo, el resultado es `const const foo = ...` o `;;`. Además, el REDUNDANT_DECLARATION de Sherlock bloqueaba los hotfixes de sintaxis legítimos.

- **LSP Boundary Sanitizer (`src/extension.ts` — `replaceSymbolCallback`):** Bloque de sanitización insertado entre la resolución del símbolo y la llamada a `edit.replace()`. El orden es intencional — `async async function` debe resolverse antes que un hipotético `async` aislado. La sanitización opera sobre `sanitizedCode` (copia de `newCode`) sin mutar el argumento original.
- **BUILD FAILURE HOTFIX EXCEPTION en `REVISOR_PROMPT` (`src/agents.ts`):** Añadida como addendum al check #6 (REDUNDANCY CHECK). Si el contexto contiene `BUILD_FAILED` o un resultado de herramienta previo que indica sintaxis corrupta o AST corruption, el agente tiene PERMISO EXPLÍCITO de re-declarar o reescribir cualquier símbolo como hotfix. En ese caso Sherlock debe emitir `"OK"` en lugar de `REDUNDANT_DECLARATION`. Lógica: cuando el build está roto, la inyección previa ya está corrupta — re-declararla es la corrección, no el error.

## [v8.2.0] - The Parallel Swarm (Concurrent Agent Orchestration)

**Objetivo:** Activar la Fase 2 de la orquestación: el Manager puede ahora delegar tareas independientes a múltiples agentes y ejecutarlos en paralelo con `Promise.all`. El motor de bloqueo de archivos de la v8.1.0 actúa como red de seguridad — si dos hilos intentan editar el mismo archivo simultáneamente, el segundo recibe un `SYSTEM LOCK` y espera. Los agentes pueden intercambiarse payloads de contexto en segundo plano sin contaminar la interfaz del usuario con JSON crudo.

- **`AgentMailbox` (`src/utils/agentMailbox.ts`):** Nuevo singleton que implementa un sistema de mensajería asíncrona entre agentes. `send(toAgentId, fromAgentId, payload)` encola un mensaje en el inbox del agente receptor. `drain(agentId)` consume y vacía el inbox, retornando los mensajes formateados como `[FROM @agentId]: payload`. `hasPending(agentId)` permite comprobar sin consumir. El mailbox es en memoria, compartido en el proceso Node.js, y persiste entre iteraciones pero no entre sesiones de VS Code.
- **`TeamCreateTool` (`src/tools/TeamCreateTool/index.ts`):** Nueva herramienta exclusiva del Manager que define un esquema de delegación paralela: `{ "team": [{"agent": "coder", "task": "..."}, {"agent": "designer", "task": "..."}] }`. La herramienta es un passthrough — su `execute()` nunca se llama. El engine la intercepta en el bloque especial de `create_team` antes de llegar al `executeTool` genérico.
- **`SendMessageTool` (`src/tools/SendMessageTool/index.ts`):** Nueva herramienta disponible para todos los agentes (Coder, Designer, Manager). `send_message({ to_agent, from_agent, payload })` escribe el payload en el `AgentMailbox` silenciosamente. El output devuelto al LLM Y a la UI es un ACK corto (`"Message queued for @designer"`), **nunca el payload completo** — así el usuario no ve JSON crudo de 200 líneas en el chat. El payload real se entrega en el contexto del receptor.
- **Parallel Swarm Engine (`src/agentEngine.ts`):** Intercept de `create_team` en el bloque de ejecución de herramientas (mismo patrón que `ask_user_approval`). Cuando el Manager llama `create_team`, el motor: (1) crea un buffer de eventos por sub-agente; (2) llama `runAgentLoop()` recursivamente para cada miembro del equipo, pasando un contexto limpio; (3) ejecuta todos con `Promise.all()` — los hilos corren concurrentemente y comparten el `FileLockManager`; (4) hace replay secuencial de todos los eventos bufferizados con separadores visuales (`━━━ @coder — thread 1/2 ━━━`) una vez que `Promise.all` resuelve. Sub-agentes que intentan escribir el mismo archivo reciben `SYSTEM LOCK` del `FileLockManager` y abortan su operación sin corromper el archivo.
- **Mailbox drain por iteración (`src/agentEngine.ts`):** Al inicio de cada iteración del bucle (antes del API call), el motor llama `AgentMailbox.drain(agentId)` e inyecta los mensajes entrantes como user turns en el historial del agente receptor. Esto permite que mensajes enviados por un agente paralelo (`send_message`) lleguen al destinatario en su próxima iteración, sin importar el orden de ejecución.
- **Auto-inject de `agent_id` (`src/agentEngine.ts`):** El motor inyecta automáticamente `args.agent_id = agentId` en cada llamada a `replace_lines` y `write_file` que no tenga ya un `agent_id` explícito. Esto elimina la responsabilidad del LLM de recordar su propio ID en cada herramienta de edición — el `FileLockManager` siempre tiene la información correcta sin instrucción adicional al agente.
- **Actualización de `AgentDefinition` en `src/agents.ts`:** `send_message` añadido al toolset de Coder y Designer. `create_team` y `send_message` añadidos al Manager. Nueva sección `PARALLEL SWARM PROTOCOL` en el system prompt del Manager con ejemplos de `create_team` y reglas de diseño de tareas independientes.

## [v8.1.0] - The Mutex Protocol (File Lock Manager)

**Objetivo:** Proteger la integridad del sistema de archivos cuando múltiples agentes ejecutan en paralelo (Fase 2: Orquestación Paralela con `Promise.all`). Sin un mecanismo de bloqueo, dos agentes corriendo concurrentemente pueden intentar escribir el mismo archivo simultáneamente, produciendo race conditions que corrompen el contenido final — el segundo write sobreescribe silenciosamente el trabajo del primero. Esta versión introduce un gestor de cerrojos en memoria que garantiza acceso mutuamente exclusivo a los archivos durante cada operación de escritura.

- **`FileLockManager` (`src/utils/lockfile.ts`):** Nuevo singleton estático que implementa el protocolo de exclusión mutua a nivel de archivo. Internamente usa un `Map<string, { agentId, acquiredAt }>` con claves normalizadas a lowercase (para case-insensitive en Windows). `acquireLock(filePath, agentId)` retorna `true` si el cerrojo está libre o si el mismo agente ya lo sostiene (reentrant), y `false` si un agente diferente lo posee. `releaseLock(filePath, agentId)` solo libera el cerrojo si el llamador es el titular actual, previniendo liberaciones accidentales cruzadas. `getHolder(filePath)` expone el agentId del titular actual para mensajes de diagnóstico.
- **Mutex en `ReplaceLinesTool` (`src/tools/ReplaceLinesTool/index.ts`):** Toda la validación previa (brace-balance, JSX-AST, anti-mass-deletion) se ejecuta SIN cerrojos — los guards son read-only y no necesitan exclusión. El `acquireLock` se llama únicamente en el punto exacto antes de `fs.writeFileSync`. Si el archivo está bloqueado por otro agente, la herramienta retorna `success: false` con el mensaje exacto `SYSTEM LOCK: El archivo [X] está siendo editado actualmente por otro agente...`. La escritura ocurre dentro de un bloque `try { fs.writeFileSync(...) } finally { releaseLock(...) }`, garantizando que el cerrojo se libere siempre, incluso si la escritura lanza una excepción inesperada.
- **Mutex en `FileWriteTool` (`src/tools/FileWriteTool/index.ts`):** Mismo patrón de cerrojo aplicado al `write_file`. `acquireLock` antes del `fs.writeFileSync`, `releaseLock` en el `finally`. El `fs.mkdirSync` (creación de directorios intermedios) también está dentro del bloque protegido, ya que es parte atómica de la operación de creación de archivo.
- **Parámetro `agent_id` (opcional) en ambas herramientas:** Se añadió `agent_id: string` como propiedad opcional en los schemas `TOOL_DEF` de `replace_lines` y `write_file`. Cuando los agentes corren en modo de orquestación paralela, cada uno pasa su identificador (ej. `"coder-1"`, `"designer-2"`) para que el sistema de cerrojos sepa quién posee qué archivo. Si `agent_id` se omite, el motor usa el valor por defecto `"agent"` — el comportamiento es compatible hacia atrás y no rompe sesiones de agente único.

## [v7.11.0] - Context Pruning (Anti Context Balloon)

- **Context Pruning:** Nueva función `pruneToolResults()` en `agentEngine.ts`. Antes de cada llamada a la API, recorre el array `messages` y trunca el contenido de cualquier mensaje `role: 'tool'` antiguo (fuera de los últimos 2 turnos) que supere 1,500 caracteres. El placeholder informativo sustituye el contenido completo para que el agente sepa que puede re-ejecutar la herramienta si lo necesita.
- **Impacto medible:** Tareas con múltiples `read_file` o `run_command` de salida larga pasarán de ~32k tokens por prompt a ~18k, reduciendo costos ~44% en escenarios de tarea larga.
- **Seguridad:** El `messages` original nunca se mutó — el pruning opera sobre una copia inmutable (`msgsToSend`). El system prompt y los mensajes del usuario nunca se truncan.
